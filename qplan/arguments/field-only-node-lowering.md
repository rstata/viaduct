# Argument for [field-only-node-lowering]

This claim concerns the pre-reasoning translation performed by `TestWorld`, not production GraphQL schema rewriting and not a claim that Viaduct's public node-resolver API has disappeared. The supported source domain contains ordinary GraphQL SDL and fragments, field resolver functions, and raw node lookup functions. A lowered node-valued field must be declared as `Node` or a subtype, every possible concrete output type must have a raw node lookup, and outputs that mix node-resolved and inline object values are excluded. Because bridge types are concrete and have no generated hierarchy, an object implementation may not narrow a Node-valued interface field's named return type; fixture composition rejects that GraphQL covariance explicitly.

The GraphQL-Java source schema remains unchanged and is retained for source validation. The separately decoded model schema rejects source names containing the reserved token `V_A`. For each Node subtype `T` actually used as a source field's named output type, model decoding adds one concrete internal type `T_V_A_Bridge { id: ID, node: T }`. These bridge types have no generated type hierarchy. For each source field `foo(args): W<T>`, where `W` is its complete list and nullability wrapper, the model schema omits `foo` and contains `foo_V_A_node(args): W<T_V_A_Bridge>` instead.

When `foo` has a source field resolver, fixture composition registers that resolver at `foo_V_A_node` and maps its source-shaped node-reference output pointwise to bridge EODs containing typed IDs. The source-facing object builder performs the same conversion for passive nested fields, while EOD storage remains strictly canonical and lowered.

Arguments occur only at `foo_V_A_node`. Consequently `foo(a)` and `foo(b)` lower to distinct `foo_V_A_node(a)` and `foo_V_A_node(b)` keys without argument transfer to `node`, which is argumentless. Null, error, and list structure are mapped recursively without changing their positions or list/nullability declarations.

Each synthetic ID encodes the concrete object type together with the raw ID. The generated resolver at `T_V_A_Bridge.node` has fixed object fragment `{ id }`; it decodes the type, checks that it is a possible type of `T`, invokes the corresponding raw node lookup, and checks that the returned object repeats the input ID. For abstract `T` and lists containing mixed concrete types, dispatch therefore occurs independently at each bridge-object occurrence.

Synthetic definitions are absent from source GraphQL text. Fixture parsing maps `foo(args) { selections }` directly to `foo_V_A_node(args) { node { selections } }`, and resolver fragments, provider paths, raw outputs, and operation selections cross the same compiler boundary. Thus source obligations correspond to a producer application at `foo_V_A_node(args)` followed by one `node` application at every non-null bridge-object occurrence. In a list, ordinary OER traversal supplies each element's list-indexed occurrence identity rather than hiding all raw node lookups inside one list-valued loader application.

The implementation tests provide finite evidence that the GraphQL-Java schema stays source-only, source Node fields are absent from the model schema, bridge fields use ordinary `id` and `node` names, `V_A` is reserved throughout source schema names, unsupported Node return covariance is rejected, and lowering preserves arguments, list shape, null/error positions, provider paths, registry edges, and per-element dispatch across all maintained resolvers. They are not a machine-checked proof. Mixed node/inline abstract outputs, malformed raw node references, missing node lookups, and directives are outside this claim.
