# Argument for [resolver-provider-containment-construction]

This claim concerns the pre-reasoning Kotlin fixture and registry construction boundary, not semantic variable execution or the TLA+ refinement boundary. Every canonical `FieldResolver` has one fixed open object fragment. Fixture-generated node loaders represent argument transfer within that fragment by selecting the bridge with resolver-owned `FromArgument` variables, so no argument-dependent fragment reconstruction can change its field-coordinate occurrences, guards, nesting, or multiplicity.

Pre-reasoning composition resolves each provider's response-key path against its alias-preserving object-fragment source, rejects lossy type conditions and ambiguous canonical occurrences, and emits an alias-free key path. `TestResolverRegistry` requires that path to match an occurrence path in its defining resolver's fixed fragment with exact keys. Registry extension consequently traverses one defining envelope and no longer computes or roots a separate `extendedVariables` fragment. The arbitrary generator explicitly inserts every chosen aliased provider path into that envelope before emitting its variable use, then invokes the same compiler used by static fixtures.

Focused `FromObjectFieldTest`, `ResolverDemandTest`, and `BranchOrderInvariantTest` cases reject absent, wrongly rooted, lossy, canonically ambiguous, argument-distinct, overlapping, and cyclic provider paths. Generator tests exercise the same compilation and ordering boundary. No current semantic resolver consumes the resulting provider metadata.
