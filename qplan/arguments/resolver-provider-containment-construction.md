# Argument for [resolver-provider-containment-construction]

This claim concerns the pre-reasoning Kotlin fixture and registry construction boundary, not semantic variable execution or the TLA+ refinement boundary. Every canonical `FieldResolver` has one fixed open parent-object fragment; its optional Query-rooted fragment is outside this object-provider claim. Fixture node lowering needs no argument transfer: source arguments remain on `foo_V_A_node`, while the argumentless `T_V_A_Bridge.node` resolver has fixed object fragment `{ id }`; genuine field-relative variables on a source resolver are constructed against that canonical producer.

Pre-reasoning composition resolves each provider's response-key path against its alias-preserving object-fragment source, rejects lossy type conditions and ambiguous canonical occurrences, and emits an alias-free key path. `TestResolverRegistry` requires that path to match an occurrence path in its defining resolver's fixed fragment with exact keys. Registry extension consequently traverses one defining envelope and no longer computes or roots a separate `extendedVariables` fragment. The arbitrary generator explicitly inserts every chosen aliased provider path into that envelope before emitting its variable use, then invokes the same compiler used by static fixtures.

Focused `FromObjectFieldTest`, `ResolverDemandTest`, and `BranchOrderInvariantTest` cases reject absent, wrongly rooted, lossy, canonically ambiguous, argument-distinct, overlapping, and cyclic provider paths. Generator tests exercise the same compilation and ordering boundary. Resolver25 and Resolver26 consume the compiled provider metadata at runtime within their documented domains.
