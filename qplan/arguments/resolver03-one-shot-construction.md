# Argument for [resolver03-one-shot-construction]

This claim concerns `semantics.resolver03` in its current variable-free domain: finite post-validation selection forests, canonical field resolvers, an acyclic resolver-demand graph, and no execution variables, directives, `@parent`, checkers, or deferred execution. It is scoped per resolver-bearing OER occurrence; distinct recursive objects, list elements, execution epochs, and otherwise equal objects are distinct occurrences and may each require their own field-resolver application.

For one concrete object occurrence, Resolver03 adds every activated resolver key's exact `extendedFragment` to the applicable selections. Each extension is the registry-computed guarded, path-rooted transitive closure of that resolver's exact object fragment, so one pass contains every applicable direct object-fragment requirement of every transitively activated resolver key. The resulting selections are grouped by concrete `Value.Key`, so duplicate selections and aliases that denote the same alias-free cell contribute their subselections to one group. `dependencyOrder` is a permutation of the unresolved key set, and the final fold constructs each grouped key exactly once after every sibling key required by its argument-specific object fragment is present in the resolved prefix.

Before a field resolver is applied, `withExtendedResolverDemand` walks its complete output demand and roots the precomputed `extendedFragment` of every nested resolver occurrence at that occurrence's guarded object path. Registry assembly computes each extension in dependency-first order, preserving exact arguments and concrete-type guards. A selective producer therefore receives the transitive passive and resolver-boundary demand required by every nested consumer before its result is projected, rather than discovering additional demand after the producer cell has been constructed.

Recursive `resolveValue` applications establish the same construction independently for each returned object occurrence and each list element. Within one object application, keys already in the resolved prefix are excluded from the unresolved set, while newly entered objects begin with their own empty result; this is the boundary between one application for one occurrence and valid repeated applications for distinct occurrences.

Deterministic counterexamples and arbitrary properties covering nested and recursive values, interfaces, unions, lists, arguments, ordinary field resolvers, and fixture-lowered node loaders provide finite evidence for the Kotlin claim. `tla/Resolver03ApplicationProof.tla` separately proves the corresponding finite extensional construction calculus under explicit extraction and alignment assumptions, but it is not a machine-checked refinement from this Kotlin function. Neither result establishes JVM scheduling or runtime side-effect behavior or extends beyond Resolver03's stated domain.
