# Argument for [resolver03-one-shot-construction]

This claim concerns `semantics.resolver03` in its current variable-free domain: finite post-validation selection forests, canonical field resolvers, a registry accepted by the conservative acyclic coordinate-level resolver-demand graph, and no execution variables, directives, `@parent`, checkers, or deferred execution. The graph may reject a world whose exact active occurrences would be acyclic, including a syntactic cycle broken by an error-valued argument; such rejection is an intentional scope restriction rather than a counterexample to this claim. The claim is scoped per resolver-bearing OER occurrence; distinct recursive objects, list elements, execution epochs, and otherwise equal objects are distinct occurrences and may each require their own field-resolver application.

For one concrete object occurrence, Resolver03 adds every activated resolver key's exact `predecessorDemand` to the applicable selections. Each predecessor demand is the registry-computed guarded, path-rooted transitive closure of that resolver's exact object fragment, so one pass contains every applicable direct object-fragment requirement of every transitively activated resolver key. The resulting selections are grouped by concrete `Value.Key`, so duplicate selections and aliases that denote the same alias-free cell contribute their subselections to one group. `dependencyOrder` is a permutation of the unresolved key set, and the final fold constructs each grouped key exactly once after every sibling key required by its argument-specific object fragment is present in the resolved prefix.

Before a field resolver is applied, `successorDemand` walks its complete output demand and roots the precomputed `predecessorDemand` of every nested resolver occurrence at that occurrence's guarded object path. Registry assembly computes each predecessor demand in dependency-first order, preserving exact arguments and concrete-type guards. A selective producer therefore receives the transitive passive and resolver-boundary demand required by every nested consumer before its result is projected, rather than discovering additional demand after the producer cell has been constructed.

`resolveValue` first constructs the complete selected passive OER beneath a produced value. It stops at null, error, and simple values, emits selected `__typename` cells directly, and omits registered resolver fields while recording their containing concrete-key paths with selections already collapsed to those objects. The recorded paths are resumed deepest first through the ordinary object resolver, passing the passive OER at that path as the initial resolved prefix. Lists are transparent to paths, so each matching list element is a distinct object occurrence receiving the same collapsed demand. Within one object continuation, keys already in the resolved prefix are excluded from the unresolved set. This preserves the boundary between one application for one occurrence and valid repeated applications for distinct occurrences without discarding passive descendants.

Deterministic counterexamples and arbitrary properties covering nested and recursive values, interfaces, unions, lists, arguments, ordinary field resolvers, and fixture-lowered node loaders provide finite evidence for the Kotlin claim. `tla/Resolver03ApplicationProof.tla` separately proves the corresponding finite extensional construction calculus under explicit extraction and alignment assumptions, but it is not a machine-checked refinement from this Kotlin function. Neither result establishes JVM scheduling or runtime side-effect behavior or extends beyond Resolver03's stated domain.
