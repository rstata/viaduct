# Qplan Current Handoff

## Working State

Qplan is a compiling Kotlin model of Viaduct query field resolution. Resolver26 is the primary algorithm and eventual implementation blueprint; the maintained earlier resolvers form the semantic and execution comparison grid documented in [`resolver-versions.md`](./resolver-versions.md).

Mutable interpretation state no longer lives in `model.Assumptions`. Shared semantics uses an `OperationContext` containing the immutable `world: Assumptions`, `VariableBindingsState`, and semantically passive resolver observer. Resolver26 extends that boundary with its request scope and explicit `cycleChecker: CycleCheckState`, `bindingDeclarationsState: BindingDeclarationsState`, and `queryValuesState: QueryValuesState` properties; the operation context does not implement those state protocols. `OEROccurrenceContext` carries the stable root, exact path, target, and optional structural parent bundle through Resolver26 object orchestration and field-resolution tasks.

`FieldResolver` now owns a selection-sensitive function relation. `FieldResolver.of` adapts existing non-selective functions by projecting their stable output in selective worlds, while `FieldResolver.ofSelective` passes runtime `SelectionForest` demand directly to a selective function without post-projection. Test-fixture registry assembly supports both forms. Resolver26 deliberately applies each producer once with the union of its bounded client and object-RSS demand; production tests that instead expose consumer-shaped applications remain disabled with passing one-shot `ALTERNATIVE` counterparts. The lasting rationale for using `of` in resolver-algorithm tests, reserving `ofSelective` for integration paths, reapplying the resolver relation during correctness validation, and treating supplied demand as a separate witness property is recorded in [`semantics/testing-contracts.md`](./semantics/testing-contracts.md#resolver-fixture-and-oracle-boundary).

Argument-bearing fields remain outside the resolver-output relation, but `FieldResolver.evaluateRelation` no longer recursively revalidates every returned object and list at runtime. Fixture construction remains responsible for producing argumentless passive output fields; the former runtime-rejection test is retained as an ignored specification test. The performance rationale and controlled measurements are recorded in [`semantics/resolver-profiling.md`](./semantics/resolver-profiling.md#2026-09-04-002258-utc).

The execution feature-test adapter now assembles selective field and node executors as selection-sensitive qplan resolvers and converts their Resolver26 successor demand into Engine API selection sets. The conversion preserves concrete applicability, nested fields, resolved arguments, lowered `V_A_typename`, and the source coordinates of Node-valued fields. It also honors `EngineConfiguration.fieldSelectivityProvider` when executor metadata does not declare selectivity. Engine-managed selective-node demand containing only the authoritative `id` returns an empty payload shell without invoking tenant node code; typename remains generated. Selective node output is projected at ingress to demanded top-level fields with registered field-resolver fields removed and omitted demanded nullable fields filled with null, retaining production ownership and coverage without admitting surplus or missing output into qplan. Twenty-one formerly `Selective`-only field tests run unchanged (18 selective-field tests and 3 required-selection tests), and 28 production selective-node tests now run unchanged. Production tests whose expected response is supported but whose callback-owned RSS, consumer-shaped execution, or repeated-materialization policy is not retain their original form as disabled `ALT` tests with passing `ALTERNATIVE` counterparts. All eighteen former `SelSem` cases in `SelectiveFieldResolversExecutionTest.kt` now have one-shot alternatives that preserve final GraphQL data and meaningful error paths while removing production materialization-cache state, invocation-order, and snapshot-reconciliation assertions. The alternatives use declarative field providers, no-RSS function providers, bounded one-shot over-fetching, stable producer results, and active resolution of argument-bearing fields. Remaining callback-RSS N/A cases require child-produced variables beneath `@parent` to parameterize ancestor work or require pruning an unused provider that qplan rejects at registry construction.

Seven production-derived conditional-directive execution tests now run unchanged. Source-document conversion preserves source response keys such as `__typename` after lowering, while static registry dependency and branch-order validation exclude `Never` selections. Of the three formerly disabled selective-field cases, two now pass unchanged; the third is an intentional sometimes-passive ownership difference and has a same-response one-shot `ALTERNATIVE` whose selective parent omits the registered descendant. The production-specific `fetchAs` null-versus-unset behavior for a conditionally excluded RSS field remains an intentional adapter difference rather than part of Resolver26 activation semantics.

Every reasoning world uses one canonical lowered `viaduct.graphql.schema.ViaductSchema`. Fields, arguments, enum values, object types, type conditions, possible-object-type sets, type expressions, resolver keys, selections, and EOD schema types come from that schema instance. Model, fixtures, arbitrary generation, semantics, and execution use `ViaductSchema` and its flat `TypeExpr` representation directly.

The model distinguishes `EngineInputData`, `EngineOutputData`, `ResolverOutputData`, and `EngineResult`. `ResolverOutputData ::= EngineOutputData | RootFieldReferenceData`, keeping symbolic references in the resolver codomain without admitting them to resolver input data. Engine results are finite graphs whose ordinary containment edges are well-founded; `ObjectEngineResult.ParentKey` is the sole distinguished backedge and references the immediate structural ancestor OER. Structural traversals skip parent keys, while finite selection-driven materialization follows them into fresh EOD projections. OER cells and paths otherwise use canonical `ObjectEngineResult.ObjectKey` values, which may retain occurrence-specific variables in their arguments. `GroundKey` remains the refinement for operations that require resolved argument values. A `ResolverOccurrenceId` combines its Query-rooted OER identity with its exact structural path; the primary result roots primary occurrences and every independently executed query fragment roots its subordinate occurrences in its own fresh Query OER. Variable instances retain their defining `ResolverOccurrenceId`; keys carry no separate occurrence identity. Result union is deliberately rejected for parent-bearing graphs until it can copy and retarget backedges correctly.

`@skip` and `@include` are lowered into `InclusionCondition`: one source occurrence is conjunctive, conflicting requirements are `Never`, and equal merged keys use a local disjunction while each occurrence's condition is pushed into only its own descendants. Resolver26 closes and launches infrastructure tasks conservatively, evaluates each merged condition after its bindings arrive, and invokes tenant resolver code only for a positively activated cell. Demand closure tracks the satisfiable disjuncts already propagated for each expanded resolver key, so an equal key that gains a late alternative also broadens its object-fragment and provider prerequisites to the same fixed point. A negatively activated cell remains physically reserved but is logically absent; resolver-input materialization filters conditioned source occurrences before response-key collection. Object- and Query-fragment provider paths remain available to decide conditions that consume `FromObjectField` or `FromQueryField` variables. Passive resolution still follows resolver source presence rather than interpreting conditions independently, and condition-aware selective-output projection remains deferred.

## Source And Lowered Schema Boundary

Fixture composition retains two distinct schemas:

- The source `GraphQLSchema` owns external GraphQL parsing, validation, source spread rules, source output types, coercion where required, and response completion.
- The canonical lowered `ViaductSchema` owns qplan fields, types, selections, resolver registry entries, conformance checks, values, and subtype reasoning. Source-backed definitions retain exact source GraphQL-Java EOD witnesses; synthetic typename definitions remain model-internal.

`GJSchema.fromSDL` parses and validates the source schema and lowers it to the final canonical `ViaductSchema`. `SourceSchemaAdapter` is the explicit source-to-lowered boundary and requires the canonical source/lowered fixture pair. Node-valued source fields retain their schema coordinates. Source-shaped node references are normalized to root-field references targeting the built-in `Query.node`; that resolver decodes the concrete type and original ID and dispatches to the matching node resolver. Typename remains compiled into ordinary synthetic field resolvers before semantic reasoning.

## Current Semantic Capabilities

All maintained resolvers support source-sensitive ownership of argumentless registered fields: an ancestor output may supply such a field passively, while an absent field uses its standard resolver. Fields with arguments are always active. The exact contract and resolver support matrix live in [`semantics/testing-contracts.md`](./semantics/testing-contracts.md).

Resolver22/23 and Resolver26 support `@parent` fields. Schema preparation validates an argument-free singular parent field and maps it to its unique argument-free child producer; child producers may return singular objects, lists, or nested lists. Resolver input validation rejects variables on every concrete branch reachable beneath a parent selection, including parent fields retargeted from abstract coordinates, while allowing variables guarded by concrete branches disjoint from all parent retargets. It otherwise preserves selective-resolver support. Each child parent cell points to its actual containing ancestor OER, but EOD materialization creates a fresh finite parent projection rather than preserving resolver-visible object identity. One-level demand lifting composes for grandparent selections. Conservative lifting may over-resolve or over-materialize ancestor demand when an active grandchild field is dynamically passive; this is an accepted tradeoff for the uncommon overlap of those features. The focused Resolver26 parent property test classifies exact variable-bearing argument selections reached across resolver boundaries beneath parents by fragment, depth, and binding-source combination, and measures diagonal dependencies in which a resolver selected below one parent independently requires its own parent.

Resolver01-03 and Resolver06-08 intentionally reject `@parent` demand. Parent-induced dependencies can require an ancestor resolver to re-enter the same still-open descendant occurrence, which cannot be represented by their local sibling ordering without adding occurrence-aware suspension or graph re-entry machinery. The maintained depth-first versions stay small for comparison and future proof work; [`examples.md`](./examples.md#why-the-depth-first-resolvers-do-not-support-parent) contains the concrete counterexample.

Resolver26 closes each OER once. Successor demand statically transposes descendant parent demand into selective producer output, while input-demand closure independently discovers parent-induced construction demand in requested descendants and reachable resolver inputs and transposes it across matching producer edges. Passive resolution therefore passes construction demand unchanged into each returned OER rather than mixing in successor invocation demand. This makes all ancestor work discoverable before child construction while retaining source-sensitive suppression of standard resolver demand. Every OER freezes after its one local launch cycle.

Resolver02/03, Resolver07/08, Resolver22/23, and Resolver26 support independently resolved Query-rooted resolver fragments. Each application receives a fresh Query OER materialized with response keys preserved, and correctness validation retains that OER as an occurrence-specific witness. The general distinction between variable producers and fragment consumers is defined in [`semantics/README.md`](./semantics/README.md#variable-production-and-consumption): `FromObjectField` and `FromQueryField` choose the provider fragment, while either the object fragment or Query fragment may consume either binding. Resolver26 implements both provider kinds and all three consumption shapes.

All maintained resolvers now support symbolic root-field references whose arguments are grounded and variable-free. A reference is executed only when its source position is demanded; a reference-bearing field omitted from non-selective demand is skipped entirely, including when the reference is a list element. Source presence takes precedence over registry membership, so a reference supplied for an argumentless registered field suppresses that field's standard resolver and input demand. Every hop uses a fresh empty Query OER for identity, the descriptor's canonical path and grounded arguments, and an empty object input typed as the target's containing type. Targets must have empty object fragments. Resolver01-23 admit only `FromArgument`; Resolver02/03, Resolver07/08, and Resolver22/23 also execute target Query fragments, while Resolver03/08/23 supply full successor demand. Direct reference results are followed as tails. Resolver01-08 perform each hop inline before continuing depth-first sibling work; Resolver21-23 perform it under their existing structured coroutine scope. Referenced composite outputs retain detached descendant OERs for ordinary active resolution even though their symbolic source cannot be structurally revisited.

Unlike production's object-only `LazyEngineObjectData` representation, a qplan reference target may return a singular scalar or enum as well as a composite object because the resolved value is published directly into the consumer cell. Ordinary abstract targets are admitted conservatively before invocation only when all of their possible concrete object types belong to the consumer's possible object types; partial overlap is rejected. A canonical `Query.node` reference instead uses the validated concrete type encoded in its ID for that same conformance check, while the resolved runtime value is still checked against the consumer field type. Resolver26 reference targets may additionally retain `FromQueryField` and provider variables, and namespace-relative requirements must be written as Query RSS with the Query-to-namespace path prefixed.

Resolver26 implements that common behavior through its conditioned passive occurrences and `FieldResolverTask`. After ordinary active-field demand reaches its fixed point, each object orchestration scans its directly demanded source fields once for reference carriers; closure itself can add active fields but cannot create new references. `ResolverOccurrenceContext` carries the publication selection, path, expected type, and construction demand; `FieldResolverTask` separately receives the publication cell and handles ordinary object fields, object-field references, list-element references, and direct reference results using one reference-tail loop. Each tail hop creates another fresh identity root while retaining the original publication identity. These roots are intentionally never shared or deduplicated; production's physical deduplication and support for target object RSS are outside qplan's semantic model. Resolver observations retain the invocation/publication link so correctness replay and application accounting can follow every hop without treating a finalized OER as relaunchable.

Every maintained resolver supports canonical `FromArgument` paths through nested input objects, with null propagation through nullable intermediate objects and no list traversal. Resolver26 additionally evaluates compiled `FromObjectField` provider paths at runtime and evaluates compiled `FromQueryField` provider paths in each occurrence's fresh Query OER. Resolver26 preserves symbolic OER keys and treats grounding as readiness and invocation data rather than a rekeying operation; distinct symbolic keys may therefore invoke the same grounded field arguments more than once.

Resolver26 supports a third `FromProvider` variable source backed by one optional suspending function on `FieldResolver`. Each active resolver occurrence invokes that function exactly once after grounding its own arguments, validates that the returned names exactly match its provider declarations, and completes the occurrence-local bindings before materializing either resolver fragment. Object- and Query-fragment work remains independently scheduled and suspends on those bindings. Provider failures complete the owning resolver field with causal error metadata and unblock dependent variable reads with error bindings.

Arbitrary registry generation has an independent `ResolverFromProviderVariablesEnabled` control. It assigns schema-compatible scalar and nested-list values derived deterministically from the owning resolver's grounded argument fingerprint, composes every generated name for one resolver into its single callback, and preserves the plans in benchmark-corpus serialization. Resolver26's `from-provider` property profile isolates this source in ordinary object fragments and hard-requires generated argument-sensitive providers, runtime applications of their owning resolvers, and observed argument-dependent callback values; deterministic contracts retain the object/Query-fragment interaction coverage. Every serialized Resolver26 broad-campaign profile also enables provider-variable generation, and the balanced profile requires runtime application of a provider-owning resolver as structural coverage evidence.

Qplan's generated property suite has a `node` profile across the maintained resolver grid and a Resolver26-only `selective-node` profile. `SelectiveNodeResolversEnabled` constructs selection-aware node dispatchers from the same complete deterministic `ObjectPlan` relation used by ordinary node properties; the callback receives node-owned demand and model-owned nonselective projection preserves the independent oracle boundary. The profile captures supplied demand and hard-requires an activated node resolver with nonempty demand, while the focused model fixture test verifies exact callback demand delivery.

The schema-embedded resolver test DSL declares deterministic provider variables with `providerVars: {name: value}`. Provider values accept GraphQL literals and the existing argument expression strings. `VariablesProviderResolverContract`, enabled only for Resolver26, covers argument-derived and multiple provider values across distinct occurrences, null bindings, provider failures, and the completed occurrence-local binding state.

Ordinary generated tests include a replayable `sometimes-passive` profile across the full maintained resolver grid. Resolver23 and Resolver26 deep stress profiles generate a schema-valid parent spine whose deepest resolver reads through three parent edges to its great-grandparent; query generation activates that path, variable insertion excludes every argument occurrence beneath a parent selection, and resolver value plans retain source-supplied `@parent` fields. The dedicated `resolver26ParentFocused` task requires generated evidence of those source-supplied fields and runs a `40:5:5` product as four reported 250-case slices. It supplements the fixed witness with two randomized parent chains of depth three or four per schema, singular and nested-list producers, nullable forms, union parent targets, scalar siblings, recursively composed diagonal demands, and directed object/Query variable attempts on those witnesses. When sometimes-passive generation is enabled, every random-parent type also contributes an argumentless constant resolver with unused parent input so ancestor-supplied values exercise speculative parent fetching without changing resolver semantics. The harness joins exact registered and applied occurrence IDs to report skipped standard resolvers with parent demand and hard-requires this intersection. Its application observer retains each fragment's materialization selections and reports per-slice `HIT`/`MISS` results plus, for each of nine runtime coverage criteria, the number of completely hitting slices and the number of contributing generated cases combined and by slice; the criteria span topology, resolver placement, variable sources and pairs, input locations, argument depth, diagonals, source/location combinations on variable-bearing diagonals, and sometimes-passive parent demand. Individual-slice misses remain diagnostic, but a miss after combining all four slices fails the task. A Resolver26-only deterministic contract independently covers Query-fragment variable use on diagonal parent demand for `FromArgument`, `FromObjectField`, and `FromQueryField`. Resolver26 broad campaign profiles also enable sometimes-passive generation and require independent evidence that registered result occurrences were supplied by their source owner without invoking the standard field resolver. Resolver26 application accounting reconstructs registered occurrences across the primary result and every request-local Query-fragment OER, qualifies observed applications by Query root and exact path, and counts sometimes-passive occurrences as the difference from that complete rooted ledger. Resolver26 application observations expose exact applied occurrence sets to from-field binding validation, which requires all and only the `FromObjectField` and `FromQueryField` bindings of applied occurrences and traverses every request-local Query root.

Ordinary generated tests now run a base-tier `root-field-reference` profile across the full maintained resolver grid. It disables fragments and variables, forces empty target fragments, and requires both generated and observed references while exercising the fixed consumer's scalar, enum, object, union, list, override, and tail positions. Resolver26's stronger exact ordinary-application-count assertion is omitted only for this profile because the consumer deliberately supplies registered fields passively; its whole-result, permutation, activation, and from-field-binding checks remain enabled.

Resolver26's additional root-field-reference property generation uses a fixed schema family surrounded and consumed by ordinary randomized schemas and registries. It provides three nested namespace levels, zero-/one-/four-argument grounded targets, fixed nested inputs, scalar and enum results, concrete-object, interface, and union results, exact two- and four-type output cycles, target Query fragments using `FromArgument` and `FromQueryField`, and resolver extensions on every concrete result type. A forced consumer supplies direct references, a mixed reference/passive list, a three-hop reference tail, and registered-resolver overrides while omitting an active-fallback sibling. Positive insertion weight additionally replaces compatible ordinary generated output positions, including concrete result positions in the middle of output trees. With node resolvers enabled, a dedicated Node resolver returns a reference to a compatible non-Node interface target; generated queries force its ID and resolver-backed extension without relying on the ordinary generated-hash oracle. `resolver26RootFieldReferenceFocused` runs a `10:5:5` product and hard-requires all of those runtime interactions, including generation and activation of the node-resolver reference. Resolver26 deep stress and every persisted broad profile impose the same ordinary and node-reference activation guards, preventing a generic stress run from silently omitting the feature.

## Execution Harness Boundary

The execution module runs validated GraphQL queries through Resolver26 and uses GraphQL Java for response completion. `EngineTestModule.runQPlanFeatureTest` adapts pre-dispatcher Engine API field and node executors into ordinary qplan fixture inputs; it does not construct production dispatchers or data loaders. When a feature test supplies a scoped executable schema, the adapter still builds the reasoning world and registry from the full schema but validates and completes the operation against the scoped schema, allowing resolver RSSes to retain private full-schema fields.

The adapter supports selective and non-selective field and node executors; field arguments; object and Query required selections; `FromArgument` variables through nested input-object paths with nullable traversal; supported singular `FromObjectField` and `FromQueryField` paths; composition of disjoint no-RSS variables-provider callbacks into one provider per field resolver; synchronous scalar, enum, list, object, error, node-reference, and root-field-reference outputs; built-in node lookup; namespace fields; and typename completion. It rejects batching field and node executors because qplan does not yet model production batching. Root-field references are recursively normalized inside object and list output before entering Resolver26. Each resolver occurrence receives the Query value materialized from its Resolver26 Query fragment. Missing nullable Query executors resolve to null, while missing non-null Query executors resolve to an error. Lossy abstract-type traversal rejected while compiling a from-field provider path is translated to the production-facing `InvalidVariableException`, so the copied union traversal validation test runs unchanged.

The adapter rejects callback providers with overlapping names or their own required selections, from-field providers whose erased production representation ambiguously matches both resolver fragments, checker and type-checker executors (including their object- and Query-rooted required selections), asynchronous EOD outputs, mutations, subscriptions, and custom scalars. Direct inline materialization of a Node-valued field remains outside the modeled execution contract: Node values enter qplan as `Query.node` references. Query fragments retain their independent fresh Query OERs; caching or deduplicating work shared with the primary operation and cross-occurrence batch coalescing remain separate execution-layer concerns.

Selective-node production tests that inspect mutable node-cache state or repeated refetch counts remain disabled in source-faithful form when that state is not part of Resolver26. Current alternatives cover conservative one-shot abstract demand without production's runtime-narrowed second-materialization snapshot, initial node-reference materialization without asserting mutation of the original production reference, reused references as fresh closed occurrences, nested RSS closure with one complete node call rather than two staged fetches, one stable producer result in place of successive cache-covering results, and a stable embedded list whose unmatched item carries an explicit dependency error. Argument-bearing client, RSS, ancestor, and fragment shapes are represented as distinct active field keys, and provider failures retain their consumer attribution without asking selective node output to own argument-bearing fields. Recursive source normalization preserves nested `EngineErrorData` so list-item dependency errors are attributed to their resolver consumers.

Production node-cache consistency tests compare contradictory successive runtime types, object shapes, or exceptions. Their one-shot alternatives retain the same GraphQL nulls, diagnostic class, and exact consumer paths using one stable node result and a consumer-local failure; each asserts one node call.

The inherited arbitrary suites in both selective-field and selective-node production ports construct a generated production `Viaduct` directly and do not expose an `EngineTestModule` adapter surface. They are N/A for this pre-dispatcher harness rather than feature blockers; qplan's generated property suites own randomized resolver coverage.

Selective-field tests that only assert production materialization source identity or the count of staged GraphQL field-fetch instrumentation callbacks are N/A. They do not add resolver-result coverage and conflict with the one-shot boundary in the same way as the intentionally omitted instrumentation feature-test files.

The latest feature-test enablement pass reduced the 43 non-`AccessChk`/`ParentFld`/`ErrorData` TODO annotations to eleven: nine copied tests now run unchanged, fifteen have passing one-shot alternatives, and eight production-only arbitrary or instrumentation harness annotations are N/A. The retained TODOs are six batching tests, three mutation-root tests, and two custom resolver-directive spelling tests. Batching-focused tests remain disabled unchanged until qplan implements batching; mutation roots are rejected by the current Query-rooted model, and arbitrary directive syntax is not carried by `SelectionForest`, so the latter two categories require model/semantic work outside the execution-only constraint of this pass.

The six selective field and node tests whose intent is to verify batching remain source-faithful and disabled with `TODO: Batching`. Singleton executor calls are not treated as batching coverage; these tests should be enabled unchanged when batching is implemented.

Production-derived execution tests live under `execution/viaductfeaturetests`. Whole-file, source-faithful preservation is the migration policy; unsupported tests remain disabled with coded reasons rather than being rewritten. [`execution/viaduct-feature-test-inventory.md`](./execution/viaduct-feature-test-inventory.md) records the current whole-file exclusions and the two ports that have drifted from their source files.

## Validation

Run ordinary qplan validation from this directory:

```shell
./gradlew check
```

Run module-specific gates while investigating a narrower boundary:

```shell
./gradlew :model:test
./gradlew :arbitrary:test
./gradlew :semantics:test
./gradlew :execution:test
```

Broad property campaigns, multithreaded stress, benchmarks, profiles, and TLA+ checks are intentionally separate. Their canonical commands and evidence standards live in the corresponding semantics and TLA documentation.

## Scope

The executor feature-test adapter is a pre-dispatcher integration surface, not a production `execution2` implementation. Future work must preserve resolver scheduling, response-key materialization, OER identity, variable occurrence identity, query-value occurrence identity, and the explicit source/lowered schema boundary. Dispatcher and data-loader integration, production `execution2` integration, custom scalars, mutations, and subscriptions remain separate work.
