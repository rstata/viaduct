## Long Term Goal

The long-term goal is a query-plan and query-execution design that supports one-shot resolver execution. One-shot is defined per resolver-bearing OER occurrence: for each field cell in the resolved result tree whose value is supplied by a resolver, all in-scope demand for that cell is aggregated before the resolver is applied, and that resolver is applied exactly once for that occurrence. Multiple client selections, RSS paths, or aliases that converge on the same alias-free OER cell must contribute to that one application. [`execution-handoff.md`](./execution-handoff.md) sketches a future demand-availability worklist executor for this model without assigning it a resolver generation number.

One-shot does not require cross-tree coalescing. Distinct OER occurrences remain distinct even when they contain the same node identifier, use the same resolver coordinate and arguments, or produce structurally equal values; resolving each occurrence separately is expected. Node caching, request deduplication, and batching may share underlying work across those occurrences, but that is a separate execution layer and is not part of the one-shot claim. Distinct list items and execution epochs likewise remain distinct occurrences.

The current model is building a plan-independent correctness judgment over `EngineResult.Object`. That judgment should characterize valid field-resolution results without mentioning planner nodes, readiness, dependency counts, or execution order, so the eventual one-shot plan and executor can be judged against it. OER coordinates are `Value.GroundKey` values carrying canonical concrete-object fields and fully coerced arguments; response aliases, response keys, response ordering, and external response assembly belong to field completion and remain outside the model. [Query Plan Research](./evergreen.md) records the production motivation, one-shot proof obligations, and hard cases.

## Current Model

### World And Schema

Each reasoning exercise fixes exactly one `Assumptions` and one canonical `Schema`. `Assumptions` supplies the schema, resolver registry, the concrete-field `behavioral` predicate, and the `selectiveResolvers` audit flag. When that flag is true, selective `resolveValue` traversal rejects any supplied `Value.Object` field absent from its resolver-demand forest. Parsing validated named fragments into a nominal type and flattened `SelectionForest`, including substitution of operation-variable bindings, is test-fixture or composition infrastructure outside the semantic model. Operation variables are distinct from the field-relative execution variables registered in `ResolverRegistry`. There are no JVM-global schema declarations.

Every schema definition has one canonical object, so ordinary `==` means that two definitions from that schema denote the same schema element; cross-schema equality is outside the model. Every non-error `Value`, `Value.Arguments`, `OpenValue`, `OpenArguments`, and `Value.Key` is constructed through a checked factory on its precise semantic category. `Value.Error` is schema-independent. Reusable schema-conformance relations live in [`model.invariants`](./model/src/main/kotlin/model/invariants/SchemaConformance.kt), and factory KDocs state the carrier-invariant postconditions they establish; because carrier implementations are sealed behind those factories, these postconditions are universally quantified over constructed values in the fixed world.

`Value.Key` is the shared alias-free open selection-key category and contains a canonical output field with `OpenArguments`. `Value.ObjectKey` refines it with a canonical `Schema.ObjectField`, and `Value.GroundKey` further requires ground `Value.Arguments`. `Value.Object.fieldValues` and `EngineResult.Object.keys` use `Value.GroundKey`, and every key present in either value is owned by that value's concrete `Schema.ObjectType`. A `Value.Object` can contain multiple values for one output field under distinct argument tuples.

`EngineResult.Object`, `EngineResult.List`, and `EngineResult.Cell` are logic-constructible model types backed by private implementations and constructed by their respective factories; they are not externally supplied implementation points. An `EngineResult.Object` is a finite, structurally comparable value tree containing its concrete type and cells only. Object construction is immutable by default; opt-in mutable objects atomically add each absent validated cell at most once, return detached cell snapshots, and throw on unset reads or repeated writes. A present object field and each list element has one `EngineResult.Cell` containing a nullable value and a check result; absence differs from a present null. Object and list factories establish recursive schema conformance for present cells, every later object write establishes the same local invariants before publication, and list results remain immutable and retain their element `typeExpr` even when empty. There is no distinct OER node-reference constructor in the canonical model.

`EngineResult?.union` is a partial structural operation. Object union requires equal object types, retains cells found in only one operand, and recursively unions cells found in both. List union is positional and requires equal element `typeExpr` values and lengths. Shared cells require equal check values; simple values union only when equal, and null unions only with null. An undefined union is represented by `IllegalArgumentException`.

### Selections And Fixture Fragments

`SpecSelection` represents GraphQL-shaped, post-validation selections solely to state their parity with the field-resolution model. [`SpecSelectionFlattener.kt`](./model/src/main/kotlin/model/spec/SpecSelectionFlattener.kt) maps them into field-resolution `Selection` occurrences. At each selection-set level, every source field occurrence contributes one member to the corresponding forest returned by this translation. That one-to-one correspondence is a postcondition of GraphQL flattening, not an invariant of every `SelectionForest`. Ordinary test fixtures perform this conversion internally and expose only the nominal type and flattened `SelectionForest`.

A `Selection` carries a canonical open `Value.Key`, possible concrete parent types, and nested selections. The key's field owner records the immediate field-lookup context, while `possibleTypes` records runtime applicability; inline fragment structure has been flattened into those two facts. A `SelectionForest` is an equality-free finite family whose `size` counts its current members. Source order is erased. `merge(type)` is the concrete-parent normalization boundary and returns an `ObjectSelectionForest`; `instantiateBindings()` is the later grounding and exact-key convergence boundary.

Semantic equality for `Selection` is intentionally undefined. `merge(type)` deliberately uses ordinary object-key equality to produce one concrete top-level selection per current key without defining selection or forest equality; `instantiateBindings()` repeats that normalization after substitution. A normalized member can therefore represent multiple source GraphQL field occurrences before or after grounding.

The test-fixture `Fragment` carrier contains a nominal composite type and a flattened, unnormalized `SelectionForest`; parsing and pre-reasoning fixture transformations preserve its field-coordinate occurrences, type guards, nesting, and multiplicity. It lives only in the model test-fixture artifact. Production correctness predicates consume forests directly, while test-only adapters preserve fragment-root diagnostics. Registry assembly validates raw fixture fragments and specializes their roots against the resolver field's concrete containing type, but canonical `FieldResolver.objectFragment` values remain open `SelectionForest`s because argument positions may contain variable templates. Fixture-generated `$node` loaders are argumentless and use the fixed fragment `{ $id }` on their bridge-object type.

### Resolver Interpretation

The resolver registry fixes field resolvers for the canonical reasoning world. Each field resolver stores one fixed open `objectFragment`, carries field-relative variable definitions, and privately stores a function from the resolved object-fragment value and ground arguments to a nullable, selection-independent `Value.Output`. Test-fixture composition uses separate `FieldResolverDefinition` values while lowering and transforming raw declarations, then registry assembly validates, specializes, and consumes each definition. Resolver01-03 stamp templates at exact OER paths, bind `fromArgument` variables from the defining occurrence's ground arguments, and ground demand before resolver application. Runtime `fromObjectField` binding remains deferred. The public `resolver(input, arguments)` application returns the complete output for non-selective reasoning, while `resolver(input, arguments, selections)` projects it with `snipToDemand`.

`snipToDemand` supplies the conceptual additional selection input by projecting a resolver's fixed output result to its demand. Holding the ordinary function inputs fixed therefore produces coherent projections for different demands. It does not close or otherwise expand that demand. Projection stops at a behavioral field before materializing its key, so symbolic arguments are permitted at that boundary while passive keys must already be instantiated.

For a canonical concrete field, `behavioral(field)` is true exactly when the field is engine-supplied `__typename` or has a registered field resolver. `snipToDemand` retains demanded passive fields and stops at those uniform behavioral boundaries. Synthetic `foo$bridge` producers and `T$Bridge.$node` loaders are ordinary registered fields, while `T$Bridge.$id` is an ordinary passive input selected explicitly by the loader's fixed fragment.

### Fixture Node Lowering

`TestWorld.fromSDL` is the compiler boundary from ordinary GraphQL SDL and fragments plus raw field and node resolver functions into the canonical field-only world. GraphQL validation uses the external schema. For every Node subtype `T` actually used as a source field's named output type, the decoded internal schema adds one concrete programmatic type `T$Bridge { $id: ID, $node: T }`; bridge types have no generated hierarchy. Every source field `foo(args): W<T>` additionally receives `foo$bridge(args): W<T$Bridge>`, preserving every list and nullability layer. Parsing lowers surface `foo(args) { selections }` to `foo$bridge(args) { $node { selections } }`.

For a source node-valued field `foo(args)` with a raw field resolver, fixture composition moves that producer to `foo$bridge(args)` and adapts its output from node references to same-shaped bridge objects containing typed IDs; passive nested node references are rewritten recursively. Arguments remain only on `foo$bridge`, so unequal tuples remain distinct without transfer variables. The generated argumentless resolver at `T$Bridge.$node` materializes `{ $id }`, dispatches the typed ID to the proper raw node lookup, and returns the lowered node object. For lists, every non-null leaf is a distinct bridge object, so ordinary list traversal gives every node lookup its own OER occurrence and path.

The lowering recursively rewrites nested raw resolver outputs and translates resolver demand between source node fields and bridge fields. It rejects a field whose possible types mix node-resolved and inline objects, and it requires every possible type of a lowered abstract node output to have a raw node resolver. Arbitrary generation therefore registers every generated `Node` implementation and keeps generated non-`Node` interfaces and unions disjoint from `Node` objects.

### Naive Depth-First Resolution

[`resolver01`](./semantics/src/main/kotlin/semantics/resolver01/Resolver.kt) merges applicable selection occurrences by their specialized `Value.GroundKey`, closes exact local field-resolver demand, topologically orders sibling dependencies, and materializes each stamped and grounded object fragment from the cells already written in the current OER. Argument errors produce error cells; an unregistered field is read from the current resolver value. Resolver01 applies each resolver non-selectively, recursively copies every passive field actually present in its finite output, and uses ordinary subselections only to locate demanded resolver boundaries.

This constructor is intentionally depth-first and may apply a resolver again when recursive demand reaches it again; it is not the one-shot execution design. [`resolver01/ResolverTest.kt`](./semantics/src/test/kotlin/semantics/resolver01/ResolverTest.kt) starts from an empty Query object and demonstrates that the construction satisfies `correctResolution` for its ordinary empty-fragment source resolvers together with nonempty fixture-generated bridge fragments.

[`resolver02`](./semantics/src/main/kotlin/semantics/resolver02/Resolver.kt) closes each concrete object's selections under the stamped and grounded object-fragment demand of activated field resolvers. [`Value.GroundKey.demandsFromSibling`](./model/src/main/kotlin/model/registry/SiblingDemand.kt) relates an exact consumer key to an exact sibling key, preserving argument tuples while interpreting type conditions. A local topological order makes already-discovered sibling inputs available to [`materialize`](./semantics/src/main/kotlin/semantics/Materialize.kt). Resolver02 applies each resolver non-selectively and treats its finite returned value as the output selection set, recursively copying every supplied passive field. Its boundary-only successor closure omits passive input leaves while retaining every path needed to discover nested resolver and `__typename` boundaries before that traversal. Existing keys are therefore excluded uniformly instead of revisiting passive subtrees.

[`resolver03`](./semantics/src/main/kotlin/semantics/resolver03/Resolver.kt) uses the same local demand closure as Resolver01-02 before dependency ordering, materialization, and recursive resolution. Separately, before applying a field resolver, it walks the output demand and recursively adds the input demand of each encountered successor resolver at that occurrence. This guarded output expansion makes passive transitive requirements visible to the producing resolver before `snipToDemand` projects its output. Shared passive construction receives that expanded demand, allocates every resolver-bearing list-transparent child OER, and populates those retained targets deepest first. Generated bridge producers and `$node` loaders use the same operations and do not introduce a distinct semantic rule.

Resolver03 aggregates transitive guarded demand before each selective resolver application. Local input closure begins with each activated resolver's fixed object fragment and repeats through every newly discovered resolver key. Output-side successor demand walks every finite object path, explores each possible concrete type of polymorphic outputs separately, and recursively roots encountered resolver requirements at their occurrence paths. Node field arguments are already exact on `foo$bridge(args)`, and every argumentless `$node` loader contributes its ordinary `{ $id }` predecessor demand at the corresponding bridge-object occurrence.

Before Resolver03 applies a resolver, it walks the supplied output demand and adds the exact predecessor demand of each resolver occurrence at its containing-object path. This leaves `snipToDemand` as a projection of exactly its supplied demand and does not inspect a producer result while deriving demand. Resolver01 and Resolver02 instead consume complete finite resolver outputs; Resolver02 uses only boundary successor demand because complete traversal already supplies passive leaves. The deterministic flat, nested, and recursive counterexamples now pass, as do the arbitrary properties covering interfaces, unions, lists, arguments, ordinary field resolvers, and fixture-lowered node loaders.

Within its current feature set, Resolver03 satisfies the scoped [`resolver03-one-shot-construction`](./claims.md) claim: it groups all applicable demand for each `Value.GroundKey` at one OER object occurrence, computes the transitive guarded requirements before resolver projection, orders required sibling cells first, and applies the resolver once while constructing that cell. Distinct recursive objects and list elements are distinct OER occurrences and therefore receive their own applications. This Kotlin design result is supported by deterministic and arbitrary tests and the argument in [`arguments/resolver03-one-shot-construction.md`](./arguments/resolver03-one-shot-construction.md); the related TLA+ theorem proves the finite extensional construction calculus, not a machine-checked refinement from the Kotlin function or a claim about the deferred features below.

### Field-Relative Variables

Resolver03 demand follows the selection-tree structure and requires every executable argument tuple to be concrete. Each resolver's predecessor demand supplies the guarded, path-rooted closure of selections required at that resolver's parent OER and below it. A depth-first traversal can therefore collect and resolve all demand below a selection before resolving the selection itself.

Resolver01-03 support `fromArgument` variables. Each resolver occurrence stamps its templates with the exact OER path, binds each stamped variable once from the occurrence's ground argument tuple, and grounds the expanded demand only after those bindings are available. Shared demand closure tracks expanded ground keys so each occurrence is bound once during one resolution; `bindFromArguments` delegates every write directly to the strict monotonic `Assumptions.bind` operation and has no idempotent-rebinding exception. Binding absence differs from a present null binding, reads of unbound variables throw, overwrites throw, and binding values are ground by type. `TestWorld.newAssumptions()` creates fresh request-local binding state over reusable schema and registry composition for tests that perform independent resolutions or permutation comparisons.

`fromObjectField` declarations, canonical provider paths, containment checks, and branch-order validation remain in pre-reasoning fixture and registry infrastructure, but no current semantic resolver evaluates those providers. The removed Resolver04 explored post-binding subtree resumption and exposed the stronger late-equality producer-demand problem; its worked counterexamples remain historical in [Resolution Algorithms By Example](./examples.md#historical-resolver04-widening-example).

### Correctness Theorems

[`semantics/theorems.md`](./semantics/theorems.md) records informal mathematical claims and supporting arguments; it is not a machine-checked proof artifact. Its current theorem is specific to Resolver02 and claims that, in its stated domain, Resolver02 produces a result satisfying `isClosedUnderResolverDemand`.

That informal theorem does not concern Resolver03, does not establish full `correctResolution`, and does not prove selective one-shot execution. The separate Resolver03 TLA+ result remains a construction-calculus theorem rather than a refinement proof for the Kotlin function.

### Resolver Demand

The externally supplied canonical resolver registry exposes an acyclic resolver-demand graph over registered concrete `Schema.ObjectField` coordinates. Registry assembly additionally uses private `Value.Variable.Template` vertices, whose structural components carry the resolver-local variable name and defining field, to order providers and reject cycles that pass through variable production. Object types are not dependency vertices.

For a registered field `f`, `registry.mayDemandFrom(f)` contains the registered object fields directly implicated by selections reachable from its fixed object fragment. In the private construction graph, variables referenced anywhere in those selections' keys add edges to their coordinates, and each variable coordinate points to the field and variable vertices implicated by its provider path. A selection directly implicates the registered object-field coordinate, when present, at each concrete possible type combined with `selection.key.field.fieldName`.

Pre-reasoning registry assembly rejects a self-cycle or longer field-variable dependency cycle with `IllegalArgumentException`.

Registry assembly uses the full private acyclic relation to process dependencies before their consumers. Provider paths need no separate root insertion because they are already occurrences in the defining fragment; variable vertices constrain the order that resolution must respect. Polymorphic outputs are traversed once per possible concrete object so their local guards and concrete resolver coordinates remain distinct.

The intended demand interpretation starts with the registered fields directly implicated by an external selection forest and takes the least superset closed under `mayDemandFrom`. The relation is intentionally a conservative coordinate-level possibility relation derived from fixed open fragment shapes rather than an exact-occurrence graph. It retains edges whose type conditions may not apply to the runtime concrete object and edges whose exact occurrence may contain `Value.Error` arguments and therefore never apply its resolver.

This is a resolver-demand graph, not a graph of every invocation input, value provenance fact, or scheduling prerequisite. Fixture lowering makes node production and loading explicit at separate registered coordinates: `foo$bridge(args)` produces bridge objects, and each `T$Bridge.$node` resolver requires the passive sibling `$id`. Dynamic output demand connects the producer to its nested loader occurrence; the loader's fixed object fragment contributes no registered sibling edge because `$id` is passive.

The graph API is defined in [`ResolverRegistry.kt`](./model/src/main/kotlin/model/registry/ResolverRegistry.kt), while assembly and invariant checks are pre-reasoning fixture infrastructure. [`ResolverDemandTest.kt`](./model/src/test/kotlin/model/registry/ResolverDemandTest.kt) exercises nested reachability, polymorphic lowered fields, bridge edges, and cycle rejection.

## Current Scope

Inputs are post-validation and all named fragment spreads are assumed to have been inlined. The `TestWorld` parsing fixture accepts one named fragment definition as a parsing envelope, ignores its name, rejects nested named spreads, and supplies its nominal type and flattened `SelectionForest` to semantic reasoning.

`@skip` and `@include` belong to the eventual field-resolution model but are deferred. Applied directives are currently rejected. Query fragments, `fromQueryField`, `@parent`, lazy executor values, checkers, and raw-versus-checked dependency distinctions are also not yet modeled. `fromArgument` variables are modeled end to end in Resolver01-03. For `fromObjectField`, declarations, provider-path compilation, open carriers, and registry validation exist, while runtime provider evaluation and binding remain deferred. `VariablesProvider` is not modeled. `EngineResult.Cell.check` remains in the carrier algebra for future checker work, but the initial `correctResolution` judgment is explicitly check-insensitive.

The current `correctResolution` judgment and Resolver01-03 require supplied operation selections and executable resolver fragments to contain no unresolved variables; operation-variable substitution is pre-reasoning parsing or composition work. The judgment does not validate field-relative provider bindings. An argument tuple containing `Value.Error` requires the error cell mandated by the OER carrier invariant and does not invoke the registered field resolver.

Every argument-bearing output field is currently assumed to have an explicit field resolver. Production namespace exceptions are outside the model.

The registry currently rejects every cycle in the conservative coordinate-level resolver-demand graph. This intentionally includes false-positive cycles whose exact active occurrences would be acyclic, such as a syntactic cycle broken by an error-valued resolver argument. `evergreen.md` records legal production RSS cycles as an eventual hard case, so conservative cycle rejection is a present scope constraint rather than a general claim about Viaduct.

Every non-node-valued, non-`__typename` Query source field has an explicit canonical field resolver at its own coordinate; every node-valued Query source field has its resolver relocated to `foo$bridge`, and canonical selections never retain surface `foo`. Canonical field resolvers are registered only at concrete object-field coordinates. Fixture inputs may provide raw node resolvers only for object types that nominally implement the canonical `Node` interface, and lowering rejects mixed node-resolved and inline possible-type sets.

## Design Constraints

Demand aggregates from consumers toward producers, while concrete type information becomes available from producers toward consumers. Do not make demand depend on first completing a scheduler decision about which concrete branch will execute. Preserve unresolved type conditions as guards until the concrete result can specialize them.

For example, if `expensive` applies only when `p` is a `B` and its object fragment requires passive field `helper`, the demand on `p` should retain the same guard:

```graphql
p {
  ... on B {
    helper
  }
}
```

This separates the semantic question, "What values must a correct result contain for each concrete type?", from the operational question, "How should an implementation schedule the work?" The current continuation addresses the semantic question first.

Requirements should be result-shaped rather than identified only by root-to-leaf syntax. Conceptually, guarded requirements describe a family:

```text
Demand : RuntimeTypeAssignment -> RequirementTree
```

Each complete runtime type assignment yields an ordinary monomorphic requirement tree. A compact implementation may share equivalent continuations, but sharing is a representation choice and is valid only when the continuation no longer depends on ancestry, target scope, ownership, or an ancestor type condition.
