# Resolver26 Design

## Status

Resolver26 is the primary qplan algorithm and eventual implementation blueprint. It is a selective query resolver based on structured concurrency and synchronous symbolic closure.

Dispatched Resolver26 field-task roots terminate their owned field and binding promises when their `Job` reaches cancelled completion, including when cancellation prevents the task body from entering. Field-resolution and helper computation boundaries convert ordinary `Exception`s into modeled outcomes; unexpected non-cancellation exceptions escaping a launched orchestration task fail the request. `Error`s escape without a cleanup guarantee. [Failure And Cancellation Protocol](#failure-and-cancellation-protocol) distinguishes the rules shared with Resolver21-23 from Resolver26-specific mechanisms.

## Root-field references

All maintained resolvers implement the common reference semantics summarized in
[`semantics/README.md`](../../../../../README.md#shared-semantic-boundaries). This section specifies
Resolver26's additional closure, condition, runtime-binding, task, and observation machinery; it is
not the capability boundary for Resolver01-23.

`ResolverOutputData ::= EngineOutputData | RootFieldReferenceData`. `RootFieldReferenceData` is therefore an opaque symbolic resolver instruction in the resolver codomain, not engine data available as resolver input. Its canonical path starts at Query, crosses only singular argumentless object namespace fields, and ends at a registered object-field resolver whose target returns a singular composite, scalar, or enum; its target arguments are already grounded and variable-free. A composite reference target conforms to its consumer only when the target's possible concrete object types are a subset of the consumer's possible object types. This conservative check occurs before invocation: an abstract target with only partial overlap is rejected even if one runtime result could have conformed. Unlike production's object-only `LazyEngineObjectData` carrier, Resolver26 may publish referenced scalar and enum values because it resolves the instruction before constructing the consumer result. The descriptor itself has no object fragment, Query fragment, or direct `@parent` relationship. Qplan additionally requires every resolver invoked as a reference target to have an empty object fragment and no `FromObjectField` variables. A target may retain Query RSS and `FromQueryField` variables, including namespace-relative input expressed by prefixing the selection with its Query-to-namespace path. This deliberate fragment restriction matches the audited tenant usage and is narrower than production Viaduct.

Ordinary active fields alone participate in `closeInputDemand`'s fixed point. Source presence takes precedence over registry membership: when a source supplies a root-field reference for a field with a registered resolver, that reference owns the occurrence and the field's standard resolver and its input demand are not activated. Once the fixed point stabilizes, closure scans directly demanded source fields for embedded references and creates root-reference occurrence contexts. A reference occupying a list-element position is likewise valid when the containing list field has a registered resolver and is being passively supplied. References nested in lists do not add closure bookkeeping: passive-value recursion reaches each concrete element occurrence and assigns it a stable pending list cell.

A reference occurrence separates stable publication state from replaceable invocation state. `ValueSourceOccurrence` is the sealed input to `FieldResolverTask`: ordinary resolver, direct root-reference, and conditioned passive-value occurrences expose their consumer selection, publication path, expected type, and construction demand. A conditioned passive-value occurrence lets the same field task activate a reference-bearing list before passive materialization begins; it does not introduce another coroutine task kind. `FieldResolverTask` extends `CoroutineFieldResolverTask<FieldPublicationOccurrence>` and owns Resolver26 setup and structured coroutine lifetime. The abstract base implements `SharedFieldResolverTask`, retains the typed publication context and field scope, and provides the common run/error boundary for Resolver21–23 and Resolver26. `FieldResolutionLogic` holds that concrete task as a constructor property and owns invocation and publication logic. The task retains its private `FieldResolutionLogic` and prepared `FieldPublicationOccurrence`, which holds the operation, containing OER occurrence, value-source occurrence, single publication cell, and provider reads; the containing OER occurrence supplies the structural parent and publication root. For each reference hop, the resolution logic creates an invocation context whose occurrence ID uses a fresh empty Query OER plus the reference path, whose object input is an empty EOD of the target field's containing type, and whose Query fragment runs in the usual independent Query-fragment OER as a child of the same field task. The grounded reference arguments immediately bind any `FromArgument` definitions; `FromProvider` and Query-fragment-sourced bindings retain their ordinary lifecycles. No namespace OER chain, detached orchestration task, object-demand closure, or target publication cell is created. The returned ordinary value is materialized only at the consumer occurrence, so simple values are published directly while object descendants and parent fields use the consumer structure.

`FieldResolverTask` ownership means that its request-root job supplies the cancellation boundary and terminal lifetime for all field-local work. `FieldResolverTask.fieldTaskScope` exposes that same structured child scope to logic executing within the task; it does not confer request-root launch capability or create a second owner. Auxiliary launches may therefore be issued by `FieldResolutionLogic` or task-owned helper operations when they are children of `fieldTaskScope`; Kotlin class placement does not determine coroutine ownership. The shared `SharedFieldResolverTask<P>` interface exposes only `publication: P`. Resolver26 supplies `FieldPublicationOccurrence` as its type argument, retaining concrete `OperationContext` access through that context. The coroutine scope stays on the task; operation, publication cell, provider reads, and occurrence metadata are accessed through their owning contexts. `FieldResolutionLogic` receives only the task and follows the same ownership path rather than storing forwarding properties or accepting a second publication-cell argument.

`FieldResolverTask` implements `ResolutionExecutionContext` and is passed explicitly to every registry function it invokes. An execution adapter may wrap that capability in an invocation-local `EngineExecutionContext`, so `resolveSelectionSet` delegates directly to the owning task without coroutine-context lookup or shared mutable binding. The task derives construction demand from the supplied materialization forest and resolves it in a fresh root OER using a child `OperationContext` whose dispatcher is derived from `fieldTaskScope`; the child context shares the logical operation's world, variable-binding state, cycle checker, binding-declaration state, and observer. Nested selection execution and every task it dispatches are consequently cancelled with the calling field task rather than becoming another top-level request.

Ordinary fields, object-field references, and list-element references use the same `FieldResolverTask`. Their occurrence context supplies the stable publication path, expected type, and construction demand; the retained publication context's cell and containing OER occurrence supply the value promise, structural parent, and publication root. For an ordinary field the task first launches its object-provider and Query-fragment children, then asks `FieldResolutionLogic` to perform the publication occurrence's inclusion and activation step, branch between ordinary symbolic-argument invocation and an already-grounded initial reference, follow one tail loop for every direct reference result, and publish normally.

If a referenced resolver directly returns another root-field reference, the shared tail-resolution loop creates another resolver occurrence with a fresh identity root, invokes the next target, and keeps the original publication identity. Every sibling reference and every tail hop has distinct root identity. Qplan intentionally does not share these roots or deduplicate equivalent descriptors; physical caching can be layered above this semantic occurrence model. Symbolic reference recursion has the same tenant-code nontermination status as other infinitely recursive resolver behavior and has no reference-specific cycle detector.

Resolver observations record both the stable publication identity and every independently rooted invocation. Correctness replay re-evaluates the source-owning resolver, consumes the exact canonical reference-hop chain needed by that output, re-evaluates each target with its empty object input, arguments, canonical completed-output demand, and Query witness, and finally checks the ordinary output at the consumer position. It does not trust the observer's recorded supplied demand; exact runtime-demand validation remains a separate application-witness property. Every invocation path must exactly equal the descriptor's grounded path, every invocation root must be fresh across the request, and every observation published beneath the result root must be consumed by one replayed chain. Application accounting uses only the observations justified by this source-ownership replay; a reference identity root contains no executable namespace occurrences or object-fragment dependencies to traverse.

## Resolver Identity

Every OER is a map whose keys compare by canonical field and argument expression. Ground keys with equal values coalesce. Symbolic keys coalesce when they contain equal variable instances in equal expression positions. A variable-bearing resolver-fragment selection retains that symbolic `ObjectKey` as its permanent cell identity; completing its bindings makes the key contextually grounded but never rekeys the cell.

Registry variables are templates. Instantiating a resolver fragment replaces all uses of each template with one variable instance identified by the concrete resolver path. Equal uses of that instance therefore coalesce within an OER, including duplicate selections and aliases that project the same canonical key. Different variable names, defining fields, or resolver paths remain distinct even when their completed bindings have equal values, so the same grounded field arguments may be invoked more than once.

Keys need no child-occurrence localization. Each object and list element owns a distinct OER, so the same symbolic key can be reused in multiple containing objects without conflating their cells. A nested resolver receives its own concrete path when its fragment is instantiated.

Resolver input materialization filters source occurrences to the concrete object type and collects them by response key. Each response group awaits every argument binding, requires its symbolic construction key to be contextually grounded, and reads that exact OER cell without substituting arguments into its identity. Duplicate occurrences in one response-key group contribute one input entry with their combined subselections. Distinct aliases remain distinct input entries even when they project one shared construction key.

Shared correctness validation has no resolver-family addressing mode. Every stored key it traverses must be contextually grounded. To validate demanded selections and reconstructed resolver input, it prefers the exact symbolic key when that cell exists and otherwise accepts the key's grounded projection, which keeps validation compatible with earlier resolver families without weakening Resolver26's runtime identity.

## Request And Task Ownership

One root `coroutineScope` owns the request. The request-scope ownership rule is normative: only orchestration-task roots and field-resolution-task roots MAY launch directly on the request scope, and every Query-fragment producer, provider reader, binding producer, or other auxiliary coroutine MUST be a child of its nearest owning task. Each OER with active work retains a distinct orchestration request-root task, while an OER with no active work freezes synchronously without launching one. The orchestration root is an architectural placeholder and ownership boundary for future asynchronous orchestration rather than a requirement imposed by today's work: its current body has no suspension point and completes its installation and freeze work during undispatched entry. Query-fragment orchestration may recursively launch more orchestration and field-task roots because those are independent tasks, while its producer coroutine and provider readers remain children of the owning field task or Query producer. Adding another request-root task kind requires an explicit update to this design and to the narrow root-task-launch capability; directly exposing or launching on the raw request scope is prohibited. `RequestScopeOwnershipTest` enforces that the raw scope is used only inside `CoroutineTaskDispatcher` and checks the permitted dispatch call sites. The shared `SharedTaskDispatcher` accepts prepared `SharedOrchestrationTask` and `SharedFieldPublicationOccurrence` handles; Resolver26 supplies request-root coroutine scheduling through `SharedOperationContext.dispatcher`. `CoroutineTaskDispatcher<O, F>` in this package is also used by Resolver21–23; its orchestration type extends `CoroutineOrchestrationTask<O>`, so dispatch checks and execution call the base directly. Typed callbacks supply field execution and cleanup. Resolver26 supplies its binding-aware cancellation handler; the default cancels the publication cell. Every asynchronously produced field publication, Query value, and provider binding is coupled to its owning job's terminal state, so cancellation before coroutine entry cannot strand a synchronously declared promise. Successful synchronous return therefore means all request work has reached quiescence.

Task completion is not a cross-task readiness protocol. Cross-task reads use OER value promises, binding promises, or an OER's bindings-declared signal. The dispatcher changes scheduling only; it does not change resolver, variable, path, or task identity.

### Failure And Cancellation Protocol

#### Rules shared by Resolver21-23 and Resolver26

Field-resolution failures are result values. Unexpected exceptions in the field task's main coroutine propagate to its `run` boundary, which completes the field's value slot with `ErrorEngineResult`. This boundary covers synchronous task setup, input materialization, resolver invocation, and passive resolution. The error does not exceptionally complete the slot or fail the request; unrelated fields can continue.

Query-fragment producers are child coroutines of the owning field task. They must catch their own computation exceptions: an exception escaping a child can cancel its parent before the parent's `run` boundary can publish a field error. Instead, a Query producer returns a `Deferred<EngineObjectOrErrorData>` carrying `Success | Error`; the owning field invokes its resolver body only after receiving the successful object variant. A materialized Query object may itself contain field-error values; those remain ordinary resolver input and are distinct from failure to produce the Query object.

Unexpected non-cancellation exceptions escaping a launched orchestration task fail the request. Neither implementation has an error-conversion catch in orchestration's `run`. Orchestration with active work runs as an independent request-root coroutine, even when a field task or Query producer dispatched it. `CoroutineStart.UNDISPATCHED` preserves synchronous installation timing but does not put that coroutine inside the dispatching caller's catch boundary. Both implementations therefore propagate an installation or freeze failure through the request job.

Synchronous orchestration preparation follows the caller's boundary. The factory's closure and initialization, `checkDispatch`, and `run` for an object with no active work execute inline. Their exceptions fail primary request setup, become the owning field's error during passive resolution, or become the Query producer's error during Query setup. A failure partway through orchestration installation can leave promises claimed before their producers were dispatched; the producer cancellation guarantee below does not cover that unfinished installation.

At each error-conversion boundary, `currentCoroutineContext().ensureActive()` distinguishes an ordinary failure from actual coroutine cancellation. If the coroutine is active, a caught `Exception`—including a task-local `CancellationException`—becomes the appropriate error value. If the coroutine has been cancelled, `ensureActive()` throws the coroutine's cancellation so Kotlin structured concurrency can propagate it. Orchestration has no such conversion boundary; cancellation there follows Kotlin's ordinary job-cancellation rules.

The canonical field-task boundary is:

```kotlin
catch (cause: Exception) {
    currentCoroutineContext().ensureActive()
    publishFieldError(cause)
}
```

The same catch pattern applies inside Query producers, substituting a Query-error outcome for `publishFieldError`. Exceptions from the error-publication code itself or from job-completion handlers remain outside that catch; declaration, ownership, and terminal-publication defects are not guaranteed to become field errors.

Cancellation is initiated on the request or a task-root `Job` and propagates to helper coroutines through Kotlin structured concurrency. Explicit cancellation cleanup for separately allocated promises belongs to task-root completion handlers; helpers do not install cancellation-cleanup handlers on their child jobs. The root handler cancels outstanding owned promises so `await()` throws `CancellationException`, including when cancellation prevents task entry. A Query `Deferred` gets its cancellation lifecycle from Kotlin. `Promise.complete(value)` and `Promise.cancel(cause)` report atomically whether the caller performed the terminal transition; root cleanup tolerates an already-completed promise.

Stopping request-owned Query-fragment tasks early because their consuming field failed or was cancelled is a non-goal. Independent Query work may finish normally. The required guarantee is that Query tasks do not remain suspended on bindings whose producers were bypassed by the consumer's failure or cancellation. Bindings still needed by those tasks must receive an error or cancellation. `QueryFragmentBindingTerminationTest` checks these exits, including "variables provider throws" and "variable missing from variables provider map", while keeping the request active and allowing finite independent Query work to finish.

Unused bindings of negatively activated work need not complete because every task that could read them is excluded by the same activation condition. Those tasks check the condition and finish before attempting to fetch the bindings, so pending bindings cannot prevent request completion. When a consumer fails or is cancelled, its Query tasks can remain active and need error or cancellation values to unblock them. With negative activation, the dependent work is also excluded, so there are no remaining readers to unblock.

None of these resolvers catches or converts `java.lang.Error` into a modeled result. An `Error` escapes unchanged for a broader fault-tolerance boundary; there is no cleanup or quiescence guarantee after such a failure. Successful synchronous resolution, by contrast, waits for request quiescence.

`CoroutineResolverContract`, exercised by all four resolvers' `CoroutineResolveTest` adapters, checks field and Query-producer errors, cancellation, JVM errors, and request failure from both primary and Query-fragment orchestration.

#### Resolver26-specific mechanisms

A nested `ctx.query` call is distinct from a resolver's declared Query fragment. The nested call runs resolver-requested selections through `FieldResolverTask.resolveSelectionSet` and returns the projected result through `semantics.shared.materializeResult`, which reads installed cells and value promises while allowing their values and bindings to remain unfinished. Result projection uses the default no-op checker, while runtime resolver inputs within the nested query still use the operation's checker. The declared Query fragment is a resolver dependency; its runtime input uses Resolver26's `materializeResolverInput`, which can reserve symbolic cells and value promises before their producers install them. Correctness replay of either object or Query-fragment inputs uses shared `materializeResult` on existing results, preserving symbolic key identity after bindings resolve.

Resolver26 starts Query production alongside object-provider readers during field-task setup, before resolution logic can suspend on bindings or activation. Each reference hop likewise starts its Query producer before invoking its variables provider. The owning invocation retains and awaits the returned `Deferred`, as in Resolver21-23. Individual `FromQueryField` readers publish variable bindings directly from the Query OER, independently of the complete materialized Query input returned by the producer. Runtime variables therefore require concurrent fragment progress without requiring an operation-wide Query-result registry; Resolver21-23 have only grounded `FromArgument` bindings.

The field-error boundary completes `FromProvider` and `FromArgument` bindings for the current resolver invocation. Each reference hop updates that invocation while retaining the original field's publication cell, so an unexpected exception releases Query tasks waiting on the failed hop's bindings and publishes the error at the original field.

Resolver26 additionally has runtime provider-binding producers. A provider reader catches failures from both inclusion-condition evaluation and path traversal and completes its binding with `VariableBinding.Error`; a false condition skips the read. A tenant variables-provider failure completes its bindings with error values and supplies an error for its owning field. Query-production failure also completes that fragment's outstanding path-variable bindings with error values. These error-conversion boundaries retain the same `ensureActive()` rule; they do not perform cancellation cleanup. The field-task root owns cancellation of object-provider, Query-provider, `FromProvider`, and delayed `FromArgument` bindings. Its dispatch-time completion handler covers the original occurrence before task entry, while invocation setup registers additional handlers on that same root job for bindings introduced by later reference hops. Query producers and provider readers rely on the root for cancellation cleanup. Resolver21-23 have no runtime binding producers, so their root cleanup only needs to terminate the field publication.

#### GraphQL execution bridge

The `CompletableFuture` translation belongs to the GraphQL execution adapter that uses Resolver26, not to the shared resolver protocol. Kotlin cancellation remains a `CancellationException` until the owning `Job` has reached its terminal cancelled state; wrapping it earlier in a non-cancellation exception would turn cancellation into task failure. After job completion the bridge completes its Java future exceptionally with `CoroutineCancellationBridgeException`, whose cause is the original Kotlin cancellation but which is not itself a `CancellationException`. Consequently Kotlin cancellation does not accidentally set that future's `isCancelled`, while explicit cancellation of the bridge future cancels its task in the opposite direction. This does not promise cancellation propagation from GraphQL Java's downstream public future; that integration gap is tracked in the qplan handoff.

### Resolver26 Operation State

`OperationContext` is the interface for this scope's stable reference bundle. It explicitly extends `SharedOperationContext<CoroutineTaskDispatcher<OrchestrationTask, FieldPublicationOccurrence>>`. Its `create(...)` factory returns an anonymous implementation delegating the shared operation properties and adding the specialized resolver observer, `cycleChecker: CycleCheckState`, and `bindingsState: BindingDeclarationsState`. The context neither implements those state protocols nor owns their mutable storage. `forChildScope` changes the dispatcher scope while retaining the same logical operation state. `FieldPublicationOccurrence` is a class implementing `OperationContext by operation`; `FieldResolverTask` supplies that occurrence through its typed `publication` property. The concrete task also retains its shared coroutine lifecycle base, original publication, and execution-bridge capability.

`OEROccurrence` bundles the root OER, exact root-relative structural path, target OER, and optional immediate parent occurrence that remain unchanged while Resolver26 orchestrates or resolves one object occurrence. Primary-operation and Query-fragment roots create self-rooted occurrences without parents. Passive object materialization creates descendant occurrences at the exact field-and-list path where each new target is published. The occurrence context is shared across resolver families, preserving the same root, path, and structural-parent identity through their common passive resolution.

## Synchronous Demand Closure

`OrchestrationTask` extends the shared `CoroutineOrchestrationTask<O>` base and supplies its `OperationContext` through `operation`. Resolver21–23 use the same lifecycle base with their own concrete operation type. The base retains the concrete operation, occurrence, and source; owns the atomic one-shot guard; calls the dispatch-validation hook after claiming dispatch; and installs field tasks before freezing the object. Resolver26 supplies the active-work predicate, passive-field validation, and field-installation hook, while retaining its private closure and binding-declaration guard. Duplicate dispatch raises `IllegalArgumentException` in both coroutine families.

`OrchestrationTask.create` synchronously computes the single closed `ObjectSelectionForest` for its concrete OER, establishes its binding-declaration domain, and installs demanded parent backedges. It returns a prepared `OrchestrationTask` implementing the shared orchestration contract with its concrete operation type, public closed demand, and stable occurrence/source properties. Construction and preparation are private to this factory: callers cannot observe an unprepared task, and the factory does not dispatch active work.

Closure repeatedly expands each newly seen resolver `ObjectKey` whose field is absent from the source EOD with that resolver's complete object fragment instantiated at the resolver path. As part of the same fixed point, it analyzes parent selections in requested descendants and reachable resolver inputs, transposes their variable-free demand across the matching producer edge, and adds the resulting ancestor demand to the containing OER. A source-present argumentless field remains unexpanded and is materialized from the source even when the registry contains its standard resolver. Expansion does not await argument bindings. It records the resolver template, its fixed input demand, and one definition for each instantiated variable.

Every source occurrence carries a conjunctive inclusion condition. Merging equal keys disjoins those occurrence conditions locally and pushes each occurrence's condition into only its own descendants. Closure therefore remains unconditional and structural: it discovers and installs every possibly needed resolver task before any condition binding must be ready. Provider paths are additionally retained without their own conditions when they produce variables consumed by conditions, preventing a condition from waiting on a provider cell whose activation depends on that same condition.

Every resolver key in closed demand is represented either by the expansion map or by an argumentless source-provided field. Successor-demand construction still transposes parent selections into selective producer output before returned objects exist, while input-demand closure independently ensures the required ancestor cells have writers. Repeating the one-level transposition through input analysis handles grandparents without recursively traversing parent backedges as structural children or reopening an ancestor task.

An open resolver key contributes its object-fragment dependencies before its arguments ground. If those arguments later become an error, those dependencies may have executed speculatively. That imprecision is accepted by the current model.

## Binding Declaration

After closure, the orchestrator declares every open binding before launching local field work.

`FromArgument` definitions owned by an already-ground key read their canonical input paths and complete immediately. A null input-object intermediate produces a null binding. Definitions owned by symbolic keys complete after the owner's arguments resolve, while the owner key itself remains unchanged.

Each `FromObjectField` definition launches a provider reader that follows its compiled path through the defining occurrence's object OER promises. Each `FromQueryField` definition launches an equivalent reader through that occurrence's fresh Query OER. Provider path templates are instantiated for the owning resolver occurrence, and provider arguments may be grounded from literals, defaults, the owner's arguments, or other acyclic from-field bindings of either kind. All binding promises are declared before provider readers and field resolvers launch.

Before reading a provider component inside an OER, its reader awaits that OER's bindings-declared signal and every argument binding needed to make the component key contextually grounded. `OrchestrationTask.create` marks bindings declared immediately after synchronous demand closure declares every binding in the OER's binding domain, before recursively materializing passive children or launching local field work.

`BindingDeclarationsState` owns these per-OER readiness signals, while `VariableBindingsState` owns actual variable-instance bindings. Binding completion reports whether it performed the terminal transition, and consumers never manufacture undeclared bindings. `FieldResolverTask` owns Query-producer launch policy and returns its child coroutine as a `Deferred<EngineObjectOrErrorData>` directly to resolution logic.

Nested provider keys resolve their argument values against the owning resolver occurrence and use the original symbolic key for OER lookup. The separately resolved arguments are a readiness and invocation witness; they do not replace the key.

Readers never insert undeclared binding promises.

## Passive Values

Every argumentless field present in a resolver's source EOD is read by canonical field name through resolver26's local `resolvePassiveValues` path, including fields that have standard resolvers in the registry, except that an engine-provided `@parent` entry is ignored in favor of the structural backedge. Source-provided argument-bearing fields are errors. A demanded registry field absent from the source uses its standard resolver; a demanded non-registry field absent from the source remains an error.

The field-resolution task uses `shared/SharedPassiveValueResolutionLogic` to resolve passive values before publishing the containing value. Resolver26's adapter supplies symbolic demand collection, its prepared orchestration factory, and dispatch for references and conditioned reference-bearing lists. The shared traversal owns object/list recursion and demand propagation; All earlier maintained resolvers also use this traversal with grounded closure and synchronous, queued, or coroutine dispatch. For each OER, the factory closes construction demand, declares and marks bindings, and installs demanded parent backedges before returning. Invocation demand separately validates selective output and guides passive descent. The traversal resolves passive fields using the returned closed demand, then hands the prepared task to `SharedOperationContext.dispatcher.dispatchOrchestrator`. Preparation belongs to orchestration; the caller controls when passive resolution is complete and dispatch may occur.

After passive children have been dispatched, the dispatcher validates the parent's materialized passive cells and enforces one-shot dispatch. An object with no active expansions freezes synchronously without creating a coroutine. Otherwise, it launches the OER's orchestration request-root task with undispatched entry; that task calls `FieldResolverTask.launchAll` to synchronously declare Query values, claim and register every active publication cell, and launch one task root per active field before freezing the OER. Nothing in the current task body needs asynchronous execution; the root exists deliberately so future orchestration work can suspend without changing the request-task architecture. Undispatched entry preserves the current contract that `dispatchOrchestrator` returns with the OER's complete cell shape installed and frozen even when the request dispatcher is queued, while any future suspension resumes normally through the orchestration root's context.

## Active Installation And Freeze

The orchestrator delegates active installation to `FieldResolverTask.launchAll`, which reserves each closed active selection's original symbolic cell, claims its value promise, registers its writer, and launches one field task before the OER freezes. A root-field reference occupying a list element likewise claims that element's pre-reserved promise before its task launches. Each ordinary task launches only its own object-provider and Query-fragment children, then its resolution logic awaits argument bindings, derives the invocation `Arguments.Ground`, completes delayed `FromArgument` bindings, and evaluates the selection's merged inclusion condition. Negative activation returns without invoking tenant code; positive activation permits the already-claimed promise to be used. Keeping reservation and writer registration synchronous preserves discoverability before freeze while moving readiness work into the conservatively launched task.

Resolver26's `CycleCheckState` is explicit operation state. Installation registers each active cell's exact writer through `operation.cycleChecker`, and provider and resolver-input reads record their dependency through the same property. Other resolvers and correctness materialization may supply a separate state or the NOP implementation; `OperationContext` does not masquerade as a cycle checker.

`reserveCell` explicitly creates an unclaimed cell placeholder when needed. `Cell.createValuePromise` claims that placeholder for the writer. Strict claiming makes disagreement between readers and writers observable.

After every local active key has claimed its symbolic cell, the orchestrator calls `freeze`. Freezing seals the OER key set and completes any unclaimed reader placeholder with a strict missing-cell exception. Claimed promises may complete or their cells may be negatively activated after the OER is frozen.

## Field Resolution

After task-local producer setup, `FieldResolutionLogic`:

1. grounds its arguments and completes any delayed `FromArgument` bindings;
2. awaits and evaluates its inclusion condition, negatively activating the cell and returning when false;
3. materializes the resolver's condition-filtered input demand from exact OER cells;
4. derives invocation successor demand from the key's closed construction demand;
5. awaits the independently orchestrated Query-rooted input;
6. records the occurrence-aware application observation;
7. invokes the selective resolver once;
8. builds the passive result shape while synchronously launching one orchestration lifecycle per OER; and
9. publishes the containing value.

Parent publication does not wait for descendant orchestration to finish. Readers independently derive and reserve the same symbolic child keys; variable-instance equality and strict reservation rules make disagreement fail rather than silently create another identity.

Query fragments reuse the defining resolver occurrence's variable bindings, retain their complete response-preserving symbolic selection tree, and use an ordinary `OrchestrationTask` rooted at an otherwise independent Query OER. The owning `FieldResolverTask` starts Query production alongside its object-path provider readers and resolution logic so a `FromQueryField` binding can ground the object fragment and a `FromObjectField` binding can ground the Query fragment without imposing an artificial fragment order. Query-provider readers complete their bindings as soon as their exact paths resolve; the owning field resolver separately awaits materialization of the complete Query input. A Query-only `FromArgument` use binds directly from the owning resolver arguments, while a binding used by both fragments is declared and completed only once. Materialization resolves arguments only to establish contextual grounding and invocation values. The OER is retained as a correctness witness under the owning resolver's exact result path.

The owning selection condition guards ordinary Query-fragment construction demand and provider reads, while explicit provider-path demand keeps the values needed to evaluate nested Query-fragment conditions available. Query-fragment materialization removes false source occurrences before response-key collection. Thus a conservatively launched Query task may produce an empty resolver-visible object and physical inactive cells without invoking the suppressed dependency resolvers.

Argument errors complete the value slot with `ErrorEngineResult` without invoking the resolver. Successful values complete the value slot once. Resolver26 does not yet publish field- or type-checker-result slots: access-check resolution and execution are future work, and checker slots are not part of the current resolver contract.

Resolver observations are semantically passive evidence. Resolver26 records Query-fragment results and application facts for validation, but replacing a normally returning, non-mutating observer with a NOP preserves semantic resolution results. Because callbacks are synchronous, an observer that throws or blocks can still change failure or latency and violates the intended instrumentation contract.

## Successor Demand

Successor demand is output projection, not input closure. It retains passive selections and argumentless resolver-bearing selections that the current resolver may supply. Argument-bearing resolver fields remain necessarily active.

Each boundary resolver's fixed object fragment contributes its passive predecessor demand transitively, conservatively including argumentless resolver-bearing fields that may be supplied by an ancestor. The original downstream construction demand continues separately into each returned child OER, where source-sensitive synchronous closure assigns only unresolved work to standard resolvers.

Successor-demand construction also transposes a selected child's `parent { ... }` demand into the containing producer selection. This static lift ensures a selective producer returns the necessary ancestor coordinates before child identity exists. The lifted portion is also included in the returned ancestor's one-shot input closure so absent fields can use their standard resolvers. Variables are prohibited beneath parent selections, so the lifted shape is fixed before occurrence-specific binding. List and nested-list child results are transparent to the ancestry relation: every contained child OER whose parent is demanded points to the same containing parent occurrence.

Sometimes-passive active fields can make transitive ancestor demand speculative. If a grandchild field with `parent.parent` demand is later supplied passively, its standard resolver need not run but the lifted ancestor demand may already have caused extra resolution or materialization. Resolver26 deliberately accepts this marginal over-work rather than making demand closure depend on a later dynamic ownership decision.

## Strictness

Binding declaration, cell reservation and claiming, writer ownership, and OER freezing are strict. Promise, cell-activation, cell-value, and binding completion operations atomically report whether each caller performed the terminal transition. Producer call sites explicitly check that result where losing would be a protocol defect; cancellation and terminal-cleanup paths intentionally tolerate losing to another terminal transition. Invalid values, missing ownership, undeclared state, and prohibited writes still throw rather than becoming a `false` completion result.

## Deliberate Scope

Resolver26 models query resolution with canonical field identity and synchronous source values. It supports runtime `FromObjectField` and `FromQueryField` bindings within their stated provider restrictions.

Correctness validation currently requires an error result only to agree with the resolver value's error variant. Exact `EngineErrorData` carrier identity and metadata agreement are deferred: fixture node lowering and other derived resolver boundaries may replace the carrier while preserving the modeled error outcome. A future error-attribution contract must first define which boundaries preserve identity and which construct a derived carrier before `correctResolution` can validate metadata without rejecting supported resolver behavior.

The current integration target excludes mutations, subscriptions, custom scalars, EOD aliases, and asynchronous EOD variants. These exclusions constrain future alignment and do not require resolver26-specific production adapters inside qplan. The separate execution feature-test adapter still rejects production `FromQueryField` recipes; that adapter boundary does not limit Resolver26's semantic capability.
